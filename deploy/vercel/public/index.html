Olist Customer Intelligence & Retention Lab

An independent, retrospective analysis of the public Olist Brazilian E-Commerce dataset (≈96k eligible orders, ≈93k customers). This page is a static dashboard; every figure it shows is returned by a Python function that recomputes the metrics from the shipped derived table on each request — the same definitions as the local Streamlit app. Nothing here is a hardcoded screenshot value.

Value concentration

Lorenz-style curve of historical merchandise value across customers. The Gini coefficient measures inequality of historical revenue per customer — it is not profit and not a forward-looking customer lifetime value.

Monthly activity

Eligible orders per calendar month, split into customers having their first order in that month (new) and customers who had ordered before (returning). Months at the edge of the dataset are incomplete and are never extrapolated.

Monthly cohort retention

Row = month of a customer's first eligible order. Column = months since that first order. A cell is the share of the cohort placing at least one order in exactly that month (not cumulative). Month 0 is 100% by construction. Cells beyond the end of the dataset are blank, never zero.

Pooled retention by month index

Size-weighted across cohorts for which that month is observable.

Time to second order

Repeaters only. Half of the customers who ever order twice do so within roughly a month.

Cumulative repeat within 12 months (mature cohorts)

Share of each cohort that ordered again at least once within 12 months. This is cumulative behaviour and cannot be produced by summing the specific-month rates above.

Rule-based customer segments

Ordered rules: insufficient history first, then long inactivity, then repeat customers split by recency and value, then one-time buyers. Recency thresholds are derived from the observed distribution of repeat-purchase gaps, not chosen by taste.

How the labels are defined

  • High-Value Active Repeat — ≥2 orders, recency within the lapsing threshold, historical value at or above the 80th percentile.
  • Active Repeat — ≥2 orders, recency within the lapsing threshold.
  • Lapsing Repeat — ≥2 orders, recency between the lapsing and inactive thresholds.
  • Recent / Dormant One-Time Buyer — exactly one order, split at the lapsing threshold.
  • Long Inactive — recency beyond the inactive threshold, whatever the order count.
  • New / Insufficient History — first order less than 60 days ago with a single order: too early to judge as inactive.

Segment labels describe the observation window. They are not churn predictions and the value column is historical revenue, not profit or CLV.

Does a poor experience predict a next order?

Outcome = the same customer places another eligible order within the window after this order. Orders whose window runs past the end of the dataset are right-censored and excluded — they are never counted as non-repeats. Intervals are 95% Wilson score intervals.

Read this as association, not cause. These are observational comparisons inside one historical dataset. Effect sizes are tiny (Cramér's V well under 0.02): with ~78k usable orders almost any difference looks "statistically significant", so the size of the association — not the p-value — is what should drive any decision. Provenance, limits and honesty notes

  • What this is. An independent retrospective case study built on a public dataset. It does not describe Olist's internal operations, and Olist has not endorsed it.
  • Identity key. A customer is a customer_unique_id, not an order. Olist's customer_id is per-order and would understate repeat behaviour.
  • Eligibility. Delivered orders only, so the retention base is consistent across time.
  • Money. Merchandise value (item prices) is kept separate from freight and from payment totals. A repeated order total is never re-summed after a one-to-many join.
  • Language. "Value" always means historical revenue. Profit, margin and CLV are not observable in this dataset.
  • Deployment shape. The shipped table is a derived, anonymised aggregate (no customer ids, cities, postcodes, review text or order ids). The function recomputes metrics from it with plain Python — no pandas in the bundle, no external API calls, no LLM dependence.
  • What is different from the local app. The Streamlit app can rebuild the pipeline from the raw CSVs from scratch. This deployment starts from the exported derived table, so pipeline-level checks are reported as they were at export time.
